## 1. Overview, Security Boundary, and Authoritative Limitations

This runbook defines the isolated, sequential Windows PowerShell procedure for operating the synthetic local Keycloak identity provider, performing first-time synthetic OIDC logins, and executing the one-time, offline two-person System Admin bootstrap for CHPMIS local development and automated testing.

### Key Constraints:
- **Synthetic only:** All identities, keys, and credentials are disposable and synthetic. No real organization IdP, real user identities, or production grants are authorized.
- **Strict loopback binding:** All host-published ports (`127.0.0.1:8081` for Keycloak, `127.0.0.1:5432` for PostgreSQL, `127.0.0.1:8000` for backend) bind exclusively to `127.0.0.1`.
- **Isolated Compose lifecycle:** Every Docker Compose command must explicitly specify `--context desktop-linux` and `--project-name chpmis011` with profile `--profile local-oidc`. Never stop, alter, or reuse containers or volumes from `chpmis010` or other projects.
- **Append-only receipt:** The bootstrap command atomically creates both `UserRole` rows (with `granted_by=NULL`) and an `AdminBootstrapReceipt` row, enforcing a zero-admin precondition and replay prevention.
- **Credential hygiene:** Passwords, client secrets, private keys, authorization codes, session cookies, and signatures must remain strictly in process memory (or the git-ignored repository-root `.env` strictly for initial Compose/Keycloak configuration). Never write signatures or keys to disk, never commit, log, or print raw secret values, and never expose sensitive cryptographic parameters as command-line arguments.

### PROMINENT SECURITY AND TRUST WARNING (R3 FINDINGS 1–3):
> **1. Operator-Supplied Keys Do Not Prove Independent Human Approvals:**
> The offline bootstrap CLI (`app.auth.bootstrap_admins`) accepts approver public keys and signatures directly from CLI arguments provided by the operator. While the tool cryptographically verifies that two distinct Ed25519 keys signed the canonical payload, **two keys generated by a local script or supplied by a single operator do NOT establish distinct human identities, legal authorization, or trusted role assignments**. In this synthetic local development slice, these signatures verify cryptographic dual-control mechanics only. Real approver identity authentication, separate human nomination, and trusted key custody remain unapproved and are strictly deferred to Human Gates (HG-1/HG-2).
>
> **2. No Approval Expiry or Instance-Bound Stale Check:**
> The canonical approval payload binds strictly to `action`, `environment`, and ordered `target_subs`. It contains **no timestamp, issued-at time, validity window, expiration claim (`exp`), or unique runtime instance nonce**. A signature generated today remains mathematically valid indefinitely for that environment and target subjects until consumed. Stale approval rejection is not implemented in the current payload schema. Any future approval expiry or replay-window policy constitutes an authorization policy change and remains unapproved and subject to Human Gate review.
>
> **3. No Operator Provenance Field or Database-Enforced Immutability:**
> The `admin_bootstrap_receipts` table records environment, target subjects, approver roles, key fingerprints, payload digest, lock flag, and creation time. It does **not record an operator identity field** (who invoked the bootstrap CLI), nor does the database enforce strict table-level immutability (e.g. via SQL REVOKE of UPDATE/DELETE or database append-only triggers); immutability is currently enforced solely via application-level logic and the unique index on `single_bootstrap_lock`. Establishing database-level immutability or auditing operator provenance requires schema and policy changes that are currently unapproved.

### 2.1 Preflight: Loopback Port Conflict Check (Fail-Closed)
Before starting any containers or processes, verify that required loopback ports (`5432`, `8081`, `8000`) are free.
This check must **fail closed** if the port query encounters an error or cannot safely verify availability.

**PowerShell Command (from repository root):**
```powershell
Set-Location "D:\ANH VU\Google Drive\VUHOCAI\Project\CHANH HUNG PMIS"

# Preflight check: loopback ports 5432, 8081, 8000
# Must fail closed if the query itself encounters an error or cannot be verified safely.
try {
    $occupiedPorts = Get-NetTCPConnection -LocalPort 5432, 8081, 8000 -ErrorAction Stop |
        Select-Object LocalAddress, LocalPort, State, OwningProcess

    if ($occupiedPorts) {
        Write-Error "PREFLIGHT FAILED: Port conflict detected on loopback ports (5432, 8081, 8000). Stop and investigate before proceeding:"
        $occupiedPorts | Format-Table -AutoSize
        exit 1
    }
} catch [System.Management.Automation.ActionPreferenceStopException] {
    # In PowerShell, Get-NetTCPConnection throws an ObjectNotFound exception when 0 matching connections exist.
    # Distinguish confirmed absence of connections from unexpected query failure.
    if ($_.CategoryInfo.Category -eq 'ObjectNotFound' -or $_.Exception.Message -match "No matching") {
        Write-Host "PREFLIGHT PASS: Confirmed ports 5432, 8081, and 8000 are available."
    } else {
        Write-Error "PREFLIGHT FAILED: Could not safely determine port availability ($($_.Exception.Message)). Failing closed."
        exit 1
    }
} catch {
    Write-Error "PREFLIGHT FAILED: Unexpected error executing port check ($($_.Exception.Message)). Failing closed."
    exit 1
}
```
*Failure Handling:* If port 5432, 8081, or 8000 is occupied, or if the port check fails, STOP. Do not stop, alter, or reuse existing containers or services (such as `chpmis010`). Resolve the port conflict or await an idle window.

## 8. Approver Key Generation and Payload Signing (Synthetic Dual Control)

> **STATUS: BLOCKED / NOT_VERIFIED — UNSAFE RUNTIME INSTRUCTIONS REMOVED**
> **DO NOT EXECUTE — NOT APPROVED**

### Concrete Missing Prerequisites and Blocking Limitations:
1. **Product Code CLI Interface Lacks Process-Memory-Only Ingestion:**
   - The offline bootstrap CLI implementation (`backend/app/auth/bootstrap_admins.py`) accepts public keys and signatures exclusively via command-line arguments (`--project-owner-key`, `--security-reviewer-key`, `--project-owner-sig`, `--security-reviewer-sig`) or file paths pointing to them.
   - Passing cryptographic keys and signatures directly as command-line arguments exposes sensitive parameters in OS process tables (`Get-Process`, `ps -ef`), shell history, and system audit logs.
   - Passing keys and signatures via file paths requires writing cryptographic artifacts to disk.
2. **Filesystem ACL Checks Do Not Guarantee Principal Exclusion:**
   - Writing keys and signatures to temporary directories (e.g. `$env:TEMP`) creates disk artifacts. Checking with `Get-Acl` for a rule naming the current user does **not** verify or guarantee that other local principals, administrators, or background services are excluded from access.
   - Security cannot be asserted based on a current-user ACL check, and creating or deleting temporary artifacts on disk violates process-memory-only credential safety constraints.
   - All unsafe executable scripts that created temporary directories, inspected ACLs, wrote signature files (`po_pub.txt`, `sr_pub.txt`, `po_sig.txt`, `sr_sig.txt`), and executed file deletions have been completely removed.
3. **Missing Safe In-Memory Seam Prerequisite:**
   - Live execution of approver key generation and payload signing remains **BLOCKED** until `backend/app/auth/bootstrap_admins.py` is enhanced (under an approved implementation task) to support a safe, process-memory-only ingestion interface (e.g. streaming signed approval payloads via standard input `stdin` or a secure memory pipe without command-line argument exposure or disk writes).
4. **Authoritative Trust and Governance Boundaries (R3 Findings 1–3):**
   - **Operator keys do not prove human identity:** Cryptographic verification of two keys generated by a local script does not authenticate independent human approver identities or legal authority.
   - **No stale check or validity window:** The canonical payload lacks timestamp, expiry (`exp`), or instance nonces; signatures remain valid indefinitely until consumed.
   - **No operator provenance or DB immutability:** Receipts do not record operator identity, and immutability is application-managed rather than database-enforced.

### 8.1 Canonical Payload Specification (Design Reference Only)
For design and verification reference, the canonical payload and signing contract defined in `backend/app/auth/bootstrap_admins.py` require:
```json
{
  "action": "bootstrap_initial_admins",
  "environment": "development",
  "target_subs": [
    "<TARGET_SUB_1>",
    "<TARGET_SUB_2>"
  ]
}
```
- **Serialization:** Strict UTF-8 encoded JSON, sorted keys (`sort_keys=True`), compact separators without whitespace (`separators=(',', ':')`).
- **Signature scheme:** Ed25519 (RFC 8032) raw public key (32 bytes) and signature (64 bytes), base64-encoded.
- **Approvers:** Two distinct keys corresponding to `project_owner` and `security_reviewer`.

### 10.2 Verification Assertions
1. `user_roles`:
   - Exactly **two** rows exist.
   - `role` is `'System Admin'` for both.
   - `granted_by` is `NULL`.
   - `second_admin_id` is `NULL`.
   - `bootstrap_receipt_id` matches the `AdminBootstrapReceipt.id`.
2. `admin_bootstrap_receipts`:
   - Exactly **one** row exists.
   - `consumed` is `true`.
   - `single_bootstrap_lock` is `'BOOTSTRAP_LOCK'` (database unique constraint preventing concurrent or second bootstrap).
   - No private keys, signatures, tokens, passwords, or personal names/emails are stored in the receipt table.
3. **Database Snapshot vs. Atomicity / Rollback Evidence (R3 Finding 8):**
   - Querying the database confirms that the post-bootstrap snapshot contains exactly two `UserRole` rows and exactly one `AdminBootstrapReceipt` row, linked by `bootstrap_receipt_id`.
   - **Timestamps do not prove atomicity:** Shared or close creation timestamps reflect execution within the database snapshot, but identical timestamps do not prove rollback or transactional atomicity.
   - **Transaction and Rollback Enforcement:** Atomicity is enforced in `backend/app/auth/bootstrap_admins.py` within an explicit SQLAlchemy database session (`with DBSession(engine) as db:`): `UserRole` entries and `AdminBootstrapReceipt` are persisted in a single transaction followed by `db.commit()`. On any failure, `db.rollback()` executes, guaranteeing zero partial writes. Unique constraint on `single_bootstrap_lock` and foreign keys enforce single-use and relational consistency.
   - **Verification of Rollback (STATUS: NOT_VERIFIED):** True atomic failure/rollback guarantees cannot be verified from a successful database snapshot. The automated unit test suite (`backend/tests/test_admin_bootstrap.py`) covers payload canonicalization, bootstrap success, argument validation, inactive users, pre-existing admin, identical keys, invalid signatures, mismatched environment, replay rejection, and CLI exit, but does **not** include an automated simulated mid-transaction failure rollback test (`test_atomic_rollback_on_failure` does not exist in `backend/tests/test_admin_bootstrap.py`). Automated verification of transactional rollback under injected failure is therefore **NOT_VERIFIED** in current test evidence.
