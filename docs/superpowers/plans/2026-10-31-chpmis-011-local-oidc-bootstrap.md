# CHPMIS-011 Implementation Plan

## Goal

Implement and verify local Keycloak OIDC code exchange and the approved one-time, two-person initial System Admin bootstrap for the CHPMIS local development environment. Keep actual agency IdP configuration, real identities, and production role grants out of scope.

## Architecture

- Add an opt-in Keycloak service to the existing Compose environment, published only on `127.0.0.1`; use the official `quay.io/keycloak/keycloak:26.8.1` image and a synthetic local realm/client. Keep the browser-facing issuer at the fixed loopback URL while backend-to-IdP token/JWKS calls use the Compose service network.
- Implement the existing `DefaultOIDCClient.exchange_code(code, redirect_uri)` protocol with bounded-timeout form-encoded token exchange, client authentication, sanitized provider errors, and no token/secret logging. Keep existing state, nonce, signature, issuer, audience, and session checks intact.
- Add a one-time `python -m app.auth.bootstrap_admins` operator command. It accepts exactly two distinct active target users, exactly two distinct approvals from the configured Project Owner and Security Reviewer key roles, and an environment identifier. Each approval is an Ed25519 signature over the same canonical payload (environment plus the ordered target subject pair); the command verifies the two public keys configured for those roles. Signature key provisioning is an offline operator step and keys/secrets are never committed.
- The command requires zero existing `System Admin` grants, creates both role rows and one append-only receipt in one database transaction, and refuses replay or any mismatch. The receipt records target user IDs, approver key fingerprints, environment, payload digest, and timestamp without storing signatures or secrets. It does not fabricate `granted_by` or normal request/approval history; the migration adds a narrowly scoped nullable bootstrap receipt reference to `UserRole` only if required by integrity, preserving existing grant history semantics.
- Treat any actual provider, approver key ownership, or real-user mapping as a separate Human Gate. Local synthetic Keycloak users and test keys prove protocol behavior only.

### Candidate C — HKLM registry trust source design (owner-approved 2026-10-31; host setup still gated)

**Proposed fixed source and reader:** Use exactly `HKLM\SOFTWARE\CHPMIS011LocalSynthetic\TrustedApprovers` in the 64-bit registry view. The Windows-host bootstrap CLI opens this constant with `KEY_QUERY_VALUE | KEY_WOW64_64KEY`; no CLI argument, environment variable, database value, caller payload, or working directory can select or override the hive, path, or view. Linux/container invocation of the bootstrap CLI fails closed as unsupported. The live runbook must execute the CLI on the Windows host, as it already does for the local backend tooling; a container cannot read this Windows trust source. Store exactly two `REG_BINARY` values, 32 bytes each: `ProjectOwnerEd25519PublicKey` and `SecurityReviewerEd25519PublicKey`. Reject missing/extra value names, wrong type or length, duplicate key bytes, malformed keys, absent registry key, registry API errors, and unsupported platforms. These public keys are integrity-sensitive but are not secret; never store private signing keys or approval signatures in the registry.

**Proposed provisioning boundary:** A separately authorized local administrator provisions the namespace before any signing request. The provisioner first inspects the exact parent/key path; if a component or value already exists outside a matching task-owned creation manifest, stop without changing it. Create only missing task-specific keys, one component at a time, using `RegCreateKeyExW` with an explicit security descriptor and non-inheriting returned handles; do not rely on inherited defaults. Proposed owner is `BUILTIN\Administrators`; use a protected DACL with full control for `SYSTEM` and `BUILTIN\Administrators`, query/read access for `BUILTIN\Users`, and no write, create-subkey, delete, write-DAC, write-owner, or create-link grants to standard users. Set that descriptor on every task-created namespace component and the trust key. Create the two values only after the protected key exists. On any uncertain or partial result, preserve task-created keys, record their exact names in a local manifest, and stop; do not recursively delete or reset pre-existing ACLs. A future exact provisioning script/commands and cleanup action require a separate review and explicit host-change authorization.

**Threat boundary and link handling:** The model trusts `SYSTEM`, local Administrators, the authorized provisioner while elevated, kernel/registry implementation, and writers of the bootstrap application. It protects against a standard local operator who is not an administrator and cannot modify HKLM namespace ancestors. Windows registry keys are securable objects, and access is checked against each key's security descriptor. Registry symbolic-link keys are followed by normal open operations unless opened specially; this proposal does not claim to detect or defend against a privileged administrator deliberately placing a link in a protected ancestor. The fresh task-specific namespace, administrator-only control of every task-created component, collision stop, and proof that the actual standard operator cannot create/delete/replace keys under those components are required for the non-admin threat boundary. If the actual ACLs or account token do not establish those facts, fail closed and leave W9 blocked. Source references: [Registry key security and access rights](https://learn.microsoft.com/en-us/windows/win32/sysinfo/registry-key-security-and-access-rights), [RegCreateKeyExW](https://learn.microsoft.com/en-us/windows/win32/api/winreg/nf-winreg-regcreatekeyexw), [registry symbolic links](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-rrp/d5ce9dcc-1f90-4f5a-b076-cc1d2c9b4195), [registry access masks](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-rrp/fefbc801-b141-4bb1-9dcb-bf366da3ae7e), and [alternate registry views](https://learn.microsoft.com/en-us/windows/win32/winprog64/accessing-an-alternate-registry-view).
