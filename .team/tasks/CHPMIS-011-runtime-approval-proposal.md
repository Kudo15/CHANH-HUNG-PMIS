- The frontend currently lacks a login UI and the callback returns JSON. A browser-driven test may be able to initiate login and navigate explicitly; whether a UI or callback change is required remains unverified and needs a separately scoped design if chosen.
- `frontend/src/components/ProjectWorkbench.tsx` loads and displays project members and can assign a task to a listed member, but source inspection found no control or request to add a staff member to a project. ### Reference checks

- Playwright's [web-server documentation](https://playwright.dev/docs/test-webserver) states `reuseExistingServer: true` may attach to an existing server, while `false` fails on an occupied URL. The repository's current `!process.env.CI` setting therefore needs explicit control in any dedicated test configuration; do not rely on the default or connect to an unrelated server.
- Playwright's [recording-options documentation](https://playwright.dev/docs/test-use-options) describes screenshot, video and trace artifacts. An eventual secure synthetic test must explicitly configure and verify its own recording and reporting behavior against the installed version, including failure output; disabling a recording type is not by itself proof all logs are secret-free.
- The [W3C Secure Contexts algorithm](https://www.w3.org/TR/secure-contexts/Overview.html#is-origin-trustworthy) classifies loopback IP origins as potentially trustworthy, and a [Chromium cookie-store test](https://chromium.googlesource.com/chromium/src/+/d4ada6fa/net/cookies/cookie_store_unittest.h) exercises a Secure cookie on `http://127.0.0.1`. Neither source proves the selected local browser build actually accepts and sends this application's cookies; the eventual live browser test must demonstrate that without weakening `Secure` or printing cookie values.
